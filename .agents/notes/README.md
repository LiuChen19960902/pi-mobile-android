# Agent Notes

**Agent Note** 是影响本代码库的设计决策或提案记录，保存代码和普通文档承载不了的内容：为什么这样做、放弃了什么、违背后会怎样重犯。本文件规定 Agent Note 放在哪里、什么时候写、写成什么格式。

当前行为和使用方法归 [README](../../README.md)、[ARCHITECTURE](../../ARCHITECTURE.md) 和 `Docs/`；协议归网关仓库的 `PROTOCOL.md`。Agent Note 链接这些文档，不复述它们。

## 目录与命名

路径同时编码生命周期和类别：`{lifecycle}/{class}/yyyy-mm-dd-topic.md`。文件名用英文小写短横线，标题和正文用中文。

- **生命周期**（顶层目录）是记录的状态，状态变化时移动文件：
  - `proposed/`：实施前评审的提案，尚未实现或只实现了一部分。
  - `implemented/`：决策已交付。记录与实际代码保持一致：之后改动移动了文件、改了符号名、默认值或机制时，在同一改动里更新记录中的这些事实；决策本身改变时见下文“取代”。
  - `rejected/`：讨论后否决的提案。只有当它的理由能挡住一个诱人且代价大的错误时才保留，否则删除。
- **类别**（第二层目录）见下表。

文件名中的日期是该主题首次提出的日期（以 Git 历史或原始记录为准）。记录之间用相对 Markdown 链接互相引用，不用纯文字或编号，以便移动后仍能检查。

不维护集中索引：按目录浏览，或用 `rg` 搜索符号、文件名、症状关键词。目录在第一次需要时创建，不提前建空目录。

## 类别

| 类别 | 范围 |
| --- | --- |
| `feature` | 面向用户的能力及其交互取舍。 |
| `bug-fix` | 修正缺陷，记录根因和防止重犯的条件。 |
| `simplification` | 删除代码、行为或界面，不新增能力。 |
| `architecture` | 已交付源码的结构与机制：分层、协议映射、状态归属、并发与终态、与 Pi 原生的对齐方式。 |
| `process` | 代码之外的工具、流程与规范：发布、隐私、协作规则。 |
| `testing` | 测试基础设施、测量方法与验证判据。 |

`architecture` 与 `process` 的分界：前者关于我们交付的源码，后者关于围绕源码的工具和流程。观察行为是否改变用来区分 `simplification` 与普通重构；不单设 `refactor`。

## 什么时候写

**非平凡改动必须在同一提交或 PR 中新增或更新至少一份 Agent Note。** 非平凡指改变了行为、协议或持久化格式、跨文件或跨仓库的约定、测试策略、流程，或做了维护者以后可能重新讨论的取舍。只做机械或局部修改、不改变行为、约定和理由的，可以不写。

- 先搜索已有记录。更新已负责该决策的记录即满足要求，不新建重复记录。
- 大的未来工作先写 `proposed/`；已做的决定直接写 `implemented/`。
- 排查中发现的易错条件（例如“只看组件级测试会假绿”）写进负责该机制的记录，不单独写一份流水账。

## 取代与合并

- 不把一份记录改写成**另一个决定**。决策被推翻时新建记录，在新旧两份中互相链接，并在旧记录中写明被哪一份取代、哪些部分仍然有效。
- 完全被取代的已实现记录可以并入新记录后删除，前提是新记录保留了旧记录中仍有价值的理由、备选方案、后果和验证要求，并修好所有入链。部分取代时两份都保留。
- 功能被整体删除时，可以把新增该功能的记录并入删除记录：保留原动机、为什么不再值得保留、放弃的能力和重新引入的条件。

## 文件格式

下列格式与上文的目录、命名规则由 `uv run --no-project python scripts/check-docs.py` 检查，提交前运行；文字规则见 [文档规范](../../Docs/AGENTS.md)。

### 头部

前三行固定为：

```markdown
# Agent Note: <标题>

Status: <状态>
```

状态取值必须与所在目录一致：

- `Status: proposed`
- `Status: implemented`
- `Status: rejected — <一句话否决理由>`

状态行不带日期或括注；日期在文件名里，其余历史在 Git 里。

### 正文

正文以 `## 问题` 开头：写清动机，不依赖解决方案也能读懂。之后的固定章节按生命周期：

**`proposed/`**

```markdown
## 问题
## 提案
…专门章节…
## 考虑过的方案
## 验收标准
## 风险
```

**`implemented/`**

```markdown
## 问题
## 决定
…专门章节…
## 考虑过的方案
## 影响
## 核对入口
```

- `## 决定` 用现在时描述已交付的实际行为，不写计划和“本轮”进度。
- `## 影响` 写这个取舍付出了什么、换来了什么，以及已知限制。
- `## 核对入口` 列源码符号、测试类名、网关文件和 Pi SDK 符号，供以后按符号重新核对；它是可选章节，但涉及具体机制时应提供。
- 协议映射、状态表等专门章节可以放在 `决定` 与 `考虑过的方案` 之间。

**`rejected/`** 保留提案原样，否决理由写在状态行；只要求头部、`## 问题`、`## 提案` 和 `## 考虑过的方案`。

### 考虑过的方案（必填）

每份记录都要写 `## 考虑过的方案`：每个真实存在过的备选方案一段，以加粗短语开头，写它为什么没被采用。没记下被否决的方案，同样的讨论就会再来一次。

备选方案只能来自真实记录，不能为了凑格式编造。确实没有记录时写：“原始记录未保留其他方案。”

## 内容规则

Agent Note 随源码公开，面向没有开发上下文的协作者。通用写作规则（只写公开信息、区分已验证与推断、废话清单）见 [文档规范](../../Docs/AGENTS.md)，此外：

- 写机制、条件和后果，不写“本轮”“负责人”“候选包”等开发过程叙述，不写内部构建号、任务编号或会话编号。需要追溯时引用公开的提交号。 <!-- check-docs: allow process-word -->
- 涉及 Pi 原生行为时写明所依据的 SDK 版本和符号名，不写 `dist/chunk-*.js` 之类会随升级变化的文件名。SDK 升级后，相关记录需要按符号重新核对。
- 具体的设备像素值、耗时和测试数量会随环境漂移，不作为结论写入；需要时只写关系或比例。
