# Agent Note: 输入草稿的归属与回填

Status: implemented

## 问题

输入框的内容有多个来源：用户手写、选择的图片、Tree 跳转时 Pi 返回的编辑器文本、切分支时取回的排队文本、发送失败后的恢复稿。早期只用“草稿为空”判断能否覆盖，导致首次自动回填的文本锁住后续跳转；切会话时自动稿被当作手写稿保留；按字符串相等认领草稿，又会误把用户改回同文的手写稿当成自动稿。

## 决定

### 归属

- 手写文字和附件按会话保存在当前进程内，新建会话时为空。未编辑过的 Tree 自动回填稿离开会话即丢弃，不保存。
- 草稿修订身份是 `inputGeneration`。恢复保存的稿件时恢复它原来的修订值；之后的任何编辑、选图、图片处理完成都从全局 `nextInputGeneration` 领取新值，不能在恢复后的旧值上 +1，否则不同稿件的修订会碰撞。
- 自动回填由修订号加会话归属记录认领：用户改字（即使改回同文）、切会话、改附件都会让记录失效。不按文案相等认领。
- 导航另有 `composerNavigationEpoch`，用来取消旧的 Tree 等待；提交时还要核对 `composerSessionId`，仅检查 `snapshot.selectedSessionId` 挡不住投影发布前的旧帧串稿。
- 图片处理 token 唯一；切会话后异步完成的结果只进入原稿槽，同一 URI 在不同会话中各自独立。已选图片允许在后台完成，导航时不取消。

### Tree 跳转的回填（对齐 Pi SDK 1.0.4）

- user / custom_message 目标：SDK 返回该条的 `editorText`，实际 leaf 落在它的父节点。当前是空稿或未编辑的上次自动稿时直接回填；有手写文字或附件时先确认，确认后等目标数据齐备再替换。
- assistant 目标：SDK 不返回 `editorText`，TUI 也不会从历史推导最近的 user。手机只移动 active leaf，保留当前文字和附件，不弹覆盖确认。
- 未知类型的目标保留确认保护。
- 流式中跳转时取回的排队文本先合并，与节点回填分开处理，避免丢待发稿。别的会话返回的 `editorText` 不污染当前稿。

### 发送受理后才清稿

- 本地 socket 写入成功早于网关 `sent`，不能据此清稿。受理时按请求 token 取不可变的提交快照，再核对所属会话、修订和附件；原稿已经移到其他槽位时只清那个槽位。
- 回显先于 `sent` 到达，或在“未确认”之后迟到时，用图片整组身份确认原稿；原始发送修订跟随有界的恢复预览保留，随预览回收。
- 选择新附件属于新编辑，不能为了让旧 `sent` 清稿而移除修订保护。

## 考虑过的方案

**AI 节点跳转时回填最近的 user 文本。** 曾作为移动端取舍实现：等待同会话、末条目等于目标 leaf 的历史页，再沿祖先链找最近的真实 user。它需要额外的等待状态和推断，且 Pi 原生没有这种行为；为与 Pi 一致已删除。

**只用“草稿为空”判断能否回填。** 首次自动稿会锁住后续所有跳转。

**跨会话全局保留一份草稿。** 切会话后旧会话的自动稿被当作手写稿带到新会话。

## 影响

- 进程结束后手写稿不保留。
- 草稿相关逻辑分散在修订号、导航 epoch 和会话归属三处，修改任一处都要核对另外两处。
- 设备测试要断言“导航请求确实发出且 leaf / 正文更新，输入不变”，不能仅凭输入没变就认为跳转成功。

## 核对入口

- `AndroidSharedStateHolder` 中的 `nextInputGeneration`、`composerNavigationEpoch`、草稿槽与发送受理逻辑。
- Pi SDK：`navigateTree` 的返回值（`editorText`、`alreadyAt`）。
