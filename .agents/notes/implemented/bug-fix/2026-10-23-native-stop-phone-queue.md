# Agent Note: 原生暂停后的手机队列副本与派发提示

Status: implemented

## 问题

桥接未持有当前 CustomEditor 时，Pi 的原生暂停会把未执行队列放回电脑输入框。只返回电脑归属标记虽然保全了文字，手机却没有后续编辑入口。根据手机提交时保存的旧正文回填也不可靠：那条输入可能已经被原生消费。

## 决定

- 只使用公开 UI API：在同一同步调用段读取原稿、调用原生 `ctx.abort()`、立即回读，并保持会话、上下文和代际不变。Pi 把队列前缀与原稿用双换行拼接；除精确分离后缀，前缀还必须完全由本实例手机已成功提交的完整消息组成，才交给手机。白名单只过滤实际回读结果，绝不据它生成或猜测恢复文本。
- `getEditorText()`可能是组件的展开表示，并非原生`getText()`的原文；若前者只返回原稿尾部，仅检查后缀就可能把原稿前半截误作队列发出。提交文本白名单作为额外隐私边界，有操作数上限并在换代清除；无法证明的CLI自发队列或编辑器转换保留电脑降级，不扩大声明。
- 白名单缓存与回读文本都有总量上限，候选迭代、匹配状态数和比较字符工作量也设硬界。仅限制队列条数不能约束带大量双换行的可分解前缀；超限放弃手机副本、保留电脑稿，不能同步阻塞原生输入循环。
- 电脑保留 Pi 原生回填的未发送草稿；手机得到的是同一份队列副本，不能自动发送。`queuedDisposition=captured` 表示已取得文本，`queuedRestoredToDesktop=true` 同时说明电脑也保留；客户端继续按当前停止操作及会话恢复一次，不覆盖后写稿。
- 无法读取或精确分离时保留既有安全降级，不根据字符串相似、旧排队快照或 `hasPendingMessages()` 猜测正文。该计数没有涵盖 TUI 压缩队列。
- `aborted.status=submitted`是同操作重试的中间回放，不消费Runtime lane或Holder停止等待。取消/超时保留新稿并提示结果未确认；未实现迟到回执恢复窗，不声称所有断连恢复已闭合。
- 原生没有公开队列明细时，手机只把已确认提交的 `sent.mode` 显示为 `Steer 已提交` / `Follow-up 已提交`。它不表示某条输入仍未执行，不产生伪造的队列正文；权威空队列、运行结束、离线、换代和模式切换清理提示。仅电脑发起而没有方式信息时仍显示通用等待提示。

## 考虑过的方案

**只恢复电脑草稿。** 能保护其他编辑器，但不满足用户离开电脑后在手机取回的目标；替代[桥接初始决定](../architecture/2026-10-20-mobile-bridge-mode.md)中的停止降级部分。独立 dequeue 仍要求桥接持有编辑器，不借别人组件动作。

**读取前后文本后重写电脑输入框。** 不需要，也可能覆盖别的编辑器变换后的状态；保留原生结果，手机仅复制能确认的前缀。

## 影响

恢复后的未发送文字会同时出现在手机和电脑；任一端都不会代用户提交它。自定义编辑器展开或变换文字而无法精确分离时，仍需到电脑查看，不把读取失败当作已经取得文字。图片队列恢复继续遵循原生仅返回文本的边界。

## 核对入口

- 网关 `bridge-extension/src/editor.ts` 的 `restoredQueuePrefix`、原生 abort 路径及 foreign-editor 合成 E2E：分别断言手机精确获得队列、电脑原稿保留、没有自动重发。
- `SharedMobileStoreTest` 检查提交方式提示的来源和清理；`AndroidSharedStateHolderTest` 检查队列副本只恢复一次，并保留手机后写稿。
- [忙时派发记录](../feature/2026-09-16-busy-dispatch-and-queue.md)仍负责本地待派发草稿、SDK 队列和发送停止按钮。
