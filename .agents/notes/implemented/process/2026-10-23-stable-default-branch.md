# Agent Note: 默认分支与稳定发布保持配套

Status: implemented

## 问题

普通 clone 获取默认分支的源码。Release 保持草稿只能限制发行附件的可见性，不能阻止用户从公开 main 获取尚未完成验证的功能。另建开发分支也不会移走 main 已有的改动，源码安装用户仍可能遇到这些问题。

## 决定

- 分支、恢复与发布 tag 的规则由[发布说明](../../../../Docs/releasing.md)维护。
- 以稳定版本的文件内容、文件模式和跨仓 CI 引用核对恢复结果；发布说明和本记录等文档差异单列，不把版本号相同当作源码一致。

## 考虑过的方案

**仅保留草稿并新建开发分支。** 公开源码的默认入口仍是 main，这不能隔离已经合入的未稳定功能。

**强推旧提交。** 会改写公共历史并影响现有 clone；普通恢复提交已能恢复工作树，没有必要。

## 影响

默认 clone 与稳定安装包使用配套实现，开发进度仍可在开发分支查看。恢复 main 不会自动修改已经下载的源码、已安装 APK 或正在运行的网关；它们需按各自升级与验证流程处理。既有已知问题仍在开发分支修复，不能把主线恢复写成这些问题已修复。

## 核对入口

- [发布说明](../../../../Docs/releasing.md)中的默认分支与发行物约定。
- 稳定 tag、发布附件校验和与 `.github/workflows/ci.yml` 的配套网关提交。
- 恢复提交相对稳定基线的逐文件内容和模式比较，以及正常 PR 必需检查。
