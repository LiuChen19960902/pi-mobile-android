# 编写项目文档

## 本项目的适配规则

先读[项目规范](../../../AGENTS.md)和[文档规范](../../../Docs/AGENTS.md)。文档职责、格式与公开范围以它们为准；涉及设计决策时，按[Agent Notes 规则](../../notes/README.md)维护对应记录，不在技能中重复维护格式。

修改文档后，从仓库根运行 `uv run --no-project python scripts/check-docs.py`；仅审查时只报告，不修改文件。

让读者能够完成当前任务，并在需要时找到依据。文档长度取决于必要信息，不设统一字数、目录或章节模板。

## 确定范围与读者

- 从用户请求和正在修改的文件确定范围；只有范围确实不明确且影响工作时才提问，不扩展为全仓库整理。
- 先定位目标项目根目录，读取适用的 `AGENTS.md`、README 和相关开发规则；遵守项目规则的范围、语言、隐私和发布约束。
- 评估或审查请求只报告；获得编写、修改或整理授权时再编辑。
- 先确定读者已经知道什么、要完成什么、如何识别成功。用户说明不要求读者理解内部文件、状态或实现细节。
- 教程按实际操作顺序展开；参考文档按查找需求组织。简短页面可以兼顾两者，内容明显增多时再拆分。

## 组织与核实

1. 阅读目标文档及必要的代码、测试或已确认决策。每个事实确定一个主要维护位置，其他文档链接过去，避免多份规则漂移。
2. 先写当前任务必需的信息：入口、操作、结果，以及相关失败和恢复方式；把实现细节留给确实需要它的读者。
3. 将已实现行为、设计提案和未验证判断写清楚。未实现的计划不能描述为现有功能；单次演示不能扩大成普遍保证。
4. 对命令和操作说明，在授权且具备条件时实际验证，并记录观察结果。缺少密钥、平台或服务时说明具体未验证项；不要为了核实文档擅自发布、付费或修改外部数据。
5. 修改原始维护位置后再更新受影响引用；生成文件应修改来源并重新生成，不能靠手工改输出隐藏不一致。只在项目确实存在相应工具时执行生成或检查命令。
6. 核对路径、链接、命令前提及事实；根据改动运行相关检查，区分实际运行、静态核对和未验证部分。写作完成后检查是否还能删除重复而不丢失条件。

README 说明当前能做什么、如何启动和验证；设计记录保留问题、决定、重要替代方案、后果及验证依据。关键概念需要解释时在首次使用处说明，不强制每页带术语表。

默认中文，除非目标项目规则或用户另有要求；不自动创建双语对照、文档网站或复杂元数据。`research/`、第三方副本、录制数据和生成文件不因文档任务而自动成为编辑范围。

需要专门精简或复核文字时，读取 [review-project-prose](../review-project-prose/SKILL.md)，保留完整事实后再调整表达。
