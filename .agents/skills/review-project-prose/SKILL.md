# 审查与精简文字

## 本项目的适配规则

先读[项目规范](../../../AGENTS.md)和[文档规范](../../../Docs/AGENTS.md)。文档职责、格式与公开范围以它们为准；涉及设计决策时，按[Agent Notes 规则](../../notes/README.md)维护对应记录，不在技能中重复维护格式。

修改文档后，从仓库根运行 `uv run --no-project python scripts/check-docs.py`；仅审查时只报告，不修改文件。

先保证信息完整，再改善表达。短不是独立验收目标；范围来自用户请求与当前变更，不能因发现其他长文而扩展。

## 保留完整事实

改写前识别以下信息，不得因压缩丢失或增强：

- 谁执行什么动作；在什么条件、时间和顺序下发生。
- 必须、可以、禁止等约束强度，以及例外和否定保证。
- 输入输出、归属、副作用、失败后果与恢复条件。
- 已验证或尚未验证、测量或估计、当前实现或未来设想。
- 防止误用所需的非显然理由，以及能够查到的证据。

代码已经表达清楚的控制流程不用逐句复述。注释保留调用者或维护者无法从局部代码看出的约束、时序、失败和理由；缺少这些信息时应补充，而不是一律删注释。

## 清理会话残留与冗余

判断一个新读者在没有聊天记录的情况下，能否理解引用并核对事实。

- “按刚才讨论”“方案 B”“审核第 7 项”等引用若只在会话内存在，改为可独立理解的决定或可访问的文件链接。
- README 和接口说明陈述当前行为。决策记录及故障复盘可以保留必要的历史、被否决方案和因果链；不要把所有历史信息都删掉。
- 去掉重复解释、自我辩护和装饰性强调；保留有意义的条件、限制以及事实上的不确定性。
- 不把运行中的旧连接/新连接等生命周期描述误判为修改历史；不删除必要的错误忽略理由、测量出处或真实待办事项。
- 术语用于准确指代机制；若“边界”“契约”“门禁”等泛词没有提供含义，就写出具体字段、规则、调用或检查。

## 执行与验收

1. 阅读指定材料和必要的事实依据。仅审查时报告具体位置、影响和修改建议；明确授权改写时再应用修改。
2. 对每处内容决定保留、补充、精简或重组，不为达到删除比例而制造修改。存在无法判定的事实时保留限定，报告缺口。
3. 移动或合并解释时更新引用。生成文档和测试录制结果要追溯来源；归档及第三方材料仅在明确指定时处理。
4. 模型提示词、工具描述和 UI 文案的措辞可能改变产品行为。不要夹带在普通润色中；属于已授权范围时按行为变化验证。
5. 对照原文核对条件、约束强度和证据是否保留，检查引用是否有效，只报告实际做过的验证。

不要求用户逐句选择措辞。已授权范围内能明确改善的内容直接处理；涉及改变业务承诺或无法核实的重要事实时再请用户决定。
